# 回収後に通常判断へ戻る候補の長期比較

状態: 元の10条件を使うPython開発比較。本採用・独立40条件ではない。安定版とRust、先行する目的評価接続20実行とその全悪化診断は保持する。

既知の準備課題10組・2,560実手で、利益の回収後に将来の本人の通常判断へ戻る候補は8組改善・2組同等・悪化0となった。H32・11手準備・初期資金不足で残っていた無駄な先送りも、全128手の利益と各手の損失内訳で解消した。ただし、確率的な世界全般への改善は未確認である。[機構の完全監査](https://github.com/iwmn-9/reflex-persona-core/tree/16a2ee1/evidence/gain_retry/complete)を次段階に進む根拠とする。

この比較では、元の競り・戦闘・資源管理・ギャンブル10条件、各128手、人格、世界乱数、H32、3本の予測標本、実際の学習、合否基準、独立40条件の予約をそのまま保持する。対照も新規に全実行する。新候補は既存の通常継続と全期間の反復継続を残したうえで、公開目的値が開始時を超えたら通常判断へ戻る継続を一つ加える。ゲーム名・行動名・準備の長さを終了条件に使わない。

実行基盤は判断・予測・将来の学習状態が一致すると確認した `3cf4fa4` を使う。既知の対応するH32計算では元の788.46875 CPU秒から158.84375 CPU秒へ短縮したが、全世界で同じ倍率になるとは主張しない。手数や標本を省く高速化ではない。候補の実行入口は4分野で中断再開後の行動・本人・乱数・保存復元が一致した。[実行基盤の確認](../../prepared_context_runtime/verification.json)、[入口の確認](https://github.com/iwmn-9/reflex-persona-core/tree/4044508/evidence/gain_retry/runner_connection)。

正本は `plan.json` と `registration.json`。全結果が揃うまで途中を合格とせず、全実手とソースを監査する。`loss_diagnosis_protocol.json` に従い、負の目的値・条件付き利得・既存参照判断差を残す全条件を対象に、登録した局面・標本数・乱数群で原因を調べる。人格による譲歩と予測・評価の不備を区別する。全世界の既定基準と全悪化・人格の確認を通った場合だけ、予約済みの独立40条件へ進む。

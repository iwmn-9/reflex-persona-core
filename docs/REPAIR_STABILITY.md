# 計画修補の予測品質を検査する部品

既定は従来のまま。`repair_guard=False` と `replan_check=False`。実際の利益が安定したという採用判断は [検証報告](../evidence/repair_stability/REPORT.md) を正本とする。機構の成立・予測上の改善・実際の利益を区別する。

## 同じ枝で参照案と比較する

`search_forecast(..., repairs=24, repair_guard=True)` は、修補を含まない同じ現在の候補群からも独立に参照案を選ぶ。候補の生成用と別の検証枝を使用できる。`select` は実際の進展マスクを両方の投票へ渡す。参照案が修補後の最優先価値層にも属するとき、対応する各枝の目的値が下がった変更を参照案へ戻す。平均値だけでは枝ごとの悪化を隠せない。

人格の最優先価値層を上書きしない。参照案がその層にない場合は保護できなかったことを明記する。別目的・別乱数枝の比較は拒否する。採用時の計画IDと記録を保ち、実際に実行した根の後だけ計画記憶を更新する。

これは有限の予測モデル内での非悪化検査。現実の成績保証・統計的な信頼区間ではない。少数の枝を増やしてもモデルの誤りは消えない。人格に沿った良いリスクを拒む可能性もあり、修正を全て止めただけなら成功としない。

## 次の公開局面で一度判断し直す

`ReplanCheck` は、参照案と修補後の候補について、選択した本人の次状態を持った仮想実行を比較する。次の公開観測で一度、ゲーム側から渡された制御器が残りを修正する。制御器へ仮想軌跡の乱数seedは渡さない。制御器は独立した固定予測枝を使い、同じ目的・人格・合法候補を保つ。進展と欲求は枝ごとの影で更新し、実学習へ合流しない。

その後は修正した共通手順と、公開情報による合法な反射を使う。未来の本人が何度も同じ検査を再帰する完全な予測ではない。現在の検査を省いた制御器を一段だけ呼ぶので、判断のずれは残る。この限定を隠して「自分を正確に先読みする」と呼ばない。

`JointForecast` の `stability_reference` と `replan_check` は任意の接続。共同計画への修補・約束の再交渉を一般化したものではない。通常の数値バッチ判断は変更しない。ゲームは観測、遷移、終了条件、目的評価、時間単位を供給する。

## 途中評価と終局を区別する

`completion_forecast(..., horizon=6, max_horizon=16)` は、全候補の全予測枝が目的の終局へ到達するか、明示された上限まで、共通の予測範囲を延ばす。現在の合法な根を残し、全候補を同じ時間単位で再生成・評価する。上限でなお途中なら、その状態を記録する。ゲーム別の有利な手や新しい評価係数は与えない。

これはゲームが持つ打切り代理スコアへの依存を減らす検査で、長い予測が正しい保証ではない。未来の手順が実行とずれること、少数のモデル枝の誤差は残る。元の仮説を長く続けた結果も、自分を完全に予測した結果と同一視しない。既存の接続例では `complete_to=16` が任意の入口、既定は0。

既に延ばした計画の残りが最初の予測幅より長い場合は、全候補の開始幅をその残りの長さまで共通に広げる。参照案だけを切り捨てず、明示した上限を超える計画は拒否する。要求した幅・残りの長さ・実際に使った幅を分けて記録する。12段の生成環境で見つけた接続不具合への一般的な修正であり、途中で止まった旧実行は全体を無効として保存し、同じ登録条件から再実行する。

## 調査から採った考え方

[Bertsekasのrollout/MPC研究](https://arxiv.org/abs/2406.00592) では、基準となる方策の評価と順次の改善を結び付ける。ここではその考え方を予測と実行の不一致を調べる材料にした。近似・人格の価値層・有限モデル枝を使う本実装へ、同じ改善定理がそのまま適用されるとは主張しない。

[SPIBB](https://arxiv.org/abs/1712.06924) は、固定データからの方策改善において不確かな領域で基準方策を使う手法。今回は学習データの訪問数や信頼境界を推定するSPIBB実装ではない。検証できない変更を基準と比較する着想だけを使った。論文のコードを組み込まず、新しい依存も追加していない。

## 再現

新しい保存先を使い、ソースを実行前に凍結する。`tools/run_repair_stability.py` の `--angle paired/feedback` は四つの既存ゲームを比較する。`--stage confirmation` は検証時と異なる条件を登録する。`tools/run_procedural_stability.py` は行動名を意味で解釈しない別の公開ルール生成環境を使う。生成した環境を結果から選別しない。全履歴を凍結コードで再実行し、別の実遷移台帳と照合する。

`--angle completion` は終局評価だけの追加と、終局評価＋修補・見直し検査を分ける。生成環境の `--length 12 --completion` も同じ比較。短い生成環境とはルールと目標配置が異なるので、二研究の勝数の差をそのまま処置効果としない。比較は同じ登録済み環境内の組に限る。

生履歴と凍結コードはローカル保存、公開は集計・事前登録・ハッシュ・得失と制約のみ。既知ゲームの接続と生成器内の確認を、未知ルールの自動理解や人間水準の完成へ拡大解釈しない。
